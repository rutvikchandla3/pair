# M2–M5: remaining milestones at PR level

Status: implementation plan, 2026-11-06. Nothing here is built. This page takes the M2–M5 rows of
[10 §2](../10-delivery-plan.md#2-pull-request-plan) and sharpens each one with what the code
showed during the checks in [README](./README.md#verification-findings): scope, the dependencies the
code reveals, and the decision a maintainer must make first. Each milestone gets the same full
per-PR specs as [M0](./m0-seam.md) and [M1](./m1-cloud-threads-docker.md) once its predecessor
lands, because M1 will settle names and seams these rows depend on. Verification per milestone is
[10 §4](../10-delivery-plan.md#4-verification-per-milestone).

How to read a row: **Scope** is what the PR does and, where it helps, what it leaves out. **Needs**
lists PRs, including ones the code adds to 10's column. **Code** names the existing code that
shapes it. **Decide first** names an open maintainer decision from
[10 §7](../10-delivery-plan.md#7-decisions-maintainers-must-make) (by number) or an engineering call.

## M2 Lifecycle and a hosted driver

Goal: an idle machine costs nothing, and a team needs no Docker host. Decide first: #2 (the hosted
vendor) at the start of M2; #3 (idle and retention defaults) before 2.1 and 2.12; #4 (model proxy
default) before 2.15; #5 (members see dollars?) before 2.17; #6 (mirror session files) before 2.19.

What the code adds to the plan:

- **Retries are fast.** The effect worker's backoff starts at 100 ms and doubles, so five attempts
  end within about 2 s ([EffectWorker.ts](../../../../apps/server/src/orchestration-v2/EffectWorker.ts)).
  A vendor's `429` or capacity error fails a sandbox almost at once until 2.4 lands. So 2.4 must ship
  before or with 2.5.
- **A delayed retry blocks its thread's queue.** A pending effect with an earlier rowid blocks newer
  ones whatever its `available_at` ([EffectOutbox.ts](../../../../apps/server/src/orchestration-v2/EffectOutbox.ts)).
  A `sandbox.start` waiting 120 s on `retryAfterMs` holds the owner thread's next effects, such as a
  checkpoint capture. That is acceptable for a sandbox that can't run anyway, but 2.4's tests must
  show other threads' effects keep moving.
- **Idle sleep is a guarded worker command.** The Scheduler has no wake-time API; it ticks every 5 s,
  and workers keep their next deadline in a `DueHint`
  ([UsageLimitRecoveryWorker.ts](../../../../apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts)).
  A rejection keeps its receipt for good, so each `sandbox.auto-sleep` takes a fresh id, as
  `thread.auto-settle` does.
- **Presence can't be the viewer signal.** Clients report presence only while another member is
  connected ([presenceReporting.ts](../../../../packages/client-runtime/src/presenceReporting.ts)), so
  the viewer lease is its own small RPC.

### 2.1 `feat(server): sleep idle sandboxes from the scheduler`

- **Scope:** `SandboxLifecycleWorker` in full: `idleDecision(inputs, now)` as a pure table-tested
  function, the viewer lease (an in-memory map renewed by a new `sandbox.viewing` RPC every 5 minutes
  while a cloud thread is visible and focused, expiring after 6), the approval hold (2 hours, then
  interrupt with a message), cap pressure (a `ready` sandbox idle 5 minutes sleeps early when a
  waiter queues), and the 7-day archived and 30-day asleep destroys. Settled threads still stop at
  once, as in M1.
- **Needs:** M1 (1.18's admission lock, 1.19's worker), 2.7 for the snapshot taken before sleep.
- **Code:** `UsageLimitRecoveryWorker`'s `DueHint` pattern; `thread.auto-settle`'s guard rules for
  rejecting when an input became live; the `sandbox_threads` membership table from 1.3 for inputs
  across attached threads.
- **Decide first:** #3.

### 2.2 `feat(server): wake sandboxes from threads, terminals, MCP, the CLI and restores`

- **Scope:** one explicit `sandbox.wake` per trigger in 04 §2: opening the thread (visible and
  focused), typing in an asleep terminal or pressing **Wake**, MCP and CLI tools that send, run or
  read files, scheduled tasks, checkpoint restore, opening a preview. Never from subscriptions,
  search, push or mirror diffs. Restore, revert and rewind park the rollback effect until `ready`
  (07 §2), with the test draining the effect worker through `waking`.
- **Needs:** 2.1.
- **Code:** wakes of a `waking` or `ready` sandbox are no-ops on dispatch's no-event allow list, so
  they don't record rejections; ids name the owner (`sandbox-wake:<id>:<owner>:<generation>`).

### 2.3 `feat(server): recycle sandboxes before a vendor's session limit`

- **Scope:** 04 §3's three steps from `capabilities.maxSessionMs`: recycle between turns, queue new
  prompts near the limit, interrupt and continue at the end. Docker has no limit, so this ships only
  for the hosted driver.
- **Needs:** 2.1, 2.5. **Code:** `RestartContinuation.ts` continues the interrupted turn.

### 2.4 `feat(server): honor retryAfterMs from compute drivers`

- **Scope:** a driver error's `retryAfterMs` sets the outbox row's `available_at`, capped (proposed:
  10 minutes), and (proposed) the attempt does not count when the error is `capacity` or `rate-limited`.
- **Needs:** M1. **Before:** 2.5 ships.
- **Code:** the retry path in `EffectWorker.ts` and `EffectOutbox.ts`; extend
  `EffectWorker.test.ts` with a case that another thread's effect runs while this one waits.

### 2.5 `feat(server): add the Vercel Sandbox compute driver` (or E2B)

## M3 Team images

Goal: admins own the machine. Decide first: #7 (recipe format and scope) before 3.2; #8 (who hears
that an agent build is ready) before 3.10; #14 (team server release form) during M3, for 5.1.

What the code adds to the plan:

- **3.1 is bigger than 10 first said.** The outbox's `thread_id` is `NOT NULL`, so the aggregate key
  needs a table rebuild (as `OrchestrationV2/EffectCancellation.ts` did). Receipts
  (`orchestration_command_receipts.aggregate_kind`) and event streams
  (`orchestration_events.aggregate_kind`) know only `project` and `thread`. Project commands commit
  through a path that writes no effects. The new aggregate needs its own lock. README decision 9
  now says so.
- **Moving sandbox effects onto a sandbox key is optional.** It would remove 1.17's hand-over queue
  move and decouple a waiting driver retry from the owner thread's other effects (see 2.4). Proposed:
  don't, unless 2.4's measurement shows turns blocked behind sandbox retries.
- **Docker's first boot copies.** 05's move of `/t3-sandbox/.image/repos` into
  `/t3-sandbox/<id>/repos` crosses from the image layer into a named volume, so it copies the clones
  and stores. 3.8 measures it before choosing between accepting the copy and mounting differently.
- **Agent authority is per message.** `HumanAuthorship.ts` records `authorId` per message, so "every
  human who wrote the current run is an active admin" is a read over the run's messages at each tool
  call.

## M4 Access and trust

Goal: members reach the machine; the server can run no agents. Decide first: #9 (previews in
cloud-only mode) and #10 (what stays on a cloud-only server) before 4.7; #11 (a Viewer role) only
if a team asks; #12 (SSH default) before 4.2.

What the code adds to the plan:

- **Open targets are forward compatible.** `RemoteOpenTargetKind` is a strict literal
  (`["tailscale", "mdns"]` in [editor.ts](../../../../packages/contracts/src/editor.ts)), but it
  travels in a `ForwardCompatibleArray`, so a `sandbox` kind is dropped by old clients, not fatal.
- **Policy files reject unknown keys** (`managedPolicyFile.ts` decodes with
  `onExcessProperty: "error"`), so a policy with `limits.cloud` fails on an older server. That is
  intended; the policy docs name the release that reads it.
- **1.13 already checks MCP bearers per sandbox.** 4.8's `/mcp`-only listener narrows the
  forward's target further; it is now hardening, not a fix.

docs; #14 (release form) by the end of M3 for 5.1; #15 (Bedrock) before 5.15; #16 (account per

What the code adds to the plan:

- **A release host already exists as a setting.** `pinnedRuntime.ts` and `t3 update` read
  `T3CODE_RELEASE_BASE_URL` ([cliRelease.ts](../../../../packages/shared/src/cliRelease.ts)), so a
  Pair release on the fork's GitHub releases installs through the existing trial and rollback.

  as 1Password's package does.

  kit's CI uses a terminal command and one cheapest-model turn (5.10).
