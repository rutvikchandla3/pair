# M2–M5: remaining milestones at PR level

Status: M0 and M1 landed; the rest is a proposal, rewritten 2026-11-08 for local-first Pair Cloud.
This page takes the M2–M5 and Later rows of [10 §2](../10-delivery-plan.md#2-pull-request-plan)
and sharpens each one with what the code shows: scope, the dependencies the code reveals, and the
decision a maintainer must make first. Each milestone gets full per-PR specs, as
[M0](./m0-seam.md) and [M1](./m1-cloud-threads-docker.md) have, while the previous milestone's gate
runs ([10 §4](../10-delivery-plan.md#milestone-gates)), because that milestone settles the names
and seams these rows depend on. M2's are written, in
[m2-pair-cloud-docker.md](./m2-pair-cloud-docker.md). The waves for each milestone are in 10 §2.

How to read a row: **Scope** is what the PR does and, where it helps, what it leaves out. **Takes**
names the owner docs' own rows it implements, since 04 §10, 05 §9, 07 §10 and 08 §9 number theirs
locally. **Needs** lists code dependencies, including ones the code adds to 10's column; merge order
also follows the gates. **Code** names the existing code that shapes it. **Decide first** names an
open maintainer decision from [10 §7](../10-delivery-plan.md#7-decisions-maintainers-must-make) (by
number) or an engineering call.

Ids are stable. A row that stays in its milestone keeps its id; a moved row, and every new row,
takes the next free id in its milestone and shows its old id as "(was 4.7)". Later rows keep their
ids until they are scheduled.

## M2 Pair Cloud on Docker (first release)

M2's full specs are in [m2-pair-cloud-docker.md](./m2-pair-cloud-docker.md), with four new rows
(2.44–2.47) and its build order. Where a spec and a row below differ, the spec wins; the rows stay
as the first sharpening the specs started from.

Goal: a team installs one always-on, cloud-only Pair Cloud server; members keep working locally
and start cloud sessions there from pushed branches; idle machines cost nothing. M2's PRs merge
after [G1](../10-delivery-plan.md#g1-m1-before-any-m2-pr-merges) passes, and M2 is done when
[G2](../10-delivery-plan.md#g2-end-of-m2) passes. Decide first: #1 (release form) before 2.36; #2
(idle and retention defaults) before 2.1 and 2.12; #3 (the App token for PR reads) and #6
(offboarding) before 2.21; #4 (fork workflows) before 2.31; #5 (upgrades interrupt agents)
before 2.37.

What the code adds to the plan:

- **Capabilities are fixed at startup.** `ServerEnvironment.ts` builds
  `ExecutionEnvironmentCapabilities` ([environment.ts](../../../../packages/contracts/src/environment.ts))
  once, so cloud-only is a startup mode, and `cloudLaunch` follows from it. Leaving the mode means a
  restart.
- **One client command still carries a placement.** The sandbox lifecycle commands are already in
  `OrchestrationV2InternalCommand`, which `dispatchCommand` can't decode
  ([rpc.test.ts](../../../../packages/contracts/src/rpc.test.ts) checks `checkpoint.rollback.fail`
  the same way). `delegated_task.request` is client-dispatchable and has an optional
  `sandbox: { sandboxId, driverId, size }`
  ([orchestrationV2.ts](../../../../packages/contracts/src/orchestrationV2.ts), around line 3650).
  Its only sender is MCP `delegate_task`, so moving the command is safe.
- **Clients gate Cloud on the driver list.** `cloudAvailability` in
  [sandbox.ts](../../../../packages/shared/src/sandbox.ts) reads `settings.sandbox.drivers`, and
  `redactServerSettingsForClient` in
  [serverSettings.ts](../../../../apps/server/src/serverSettings.ts) hides only secret values. So
  member redaction keeps each driver's `kind`, `id`, `label` and `size`.
- **A missing branch is created silently.** `checkoutInSandbox` in
  [CloudPreparation.ts](../../../../apps/server/src/sandbox/lifecycle/CloudPreparation.ts) checks
  out `origin/<branch>` if it exists and otherwise creates `branch` from `origin/<baseRef>`. M1
  mobile sends a freshly generated `branch`, so the unpushed check needs its own key.
- **`historyOrigin` decodes strictly.** `OrchestrationV2ThreadHistoryOrigin` is
  `Schema.Literals(["native", "v1_import"])`, and `ForwardCompatibleOptional` already exists in
  [baseSchemas.ts](../../../../packages/contracts/src/baseSchemas.ts).
- **One member sends no pushes.** `isTeamMode` in
  [TeamState.ts](../../../../apps/server/src/team/TeamState.ts) needs more than one active member,
  and `ws.ts` sets `ServerConfig.memberPush` only in team mode.
- **Webhook URLs come only from the relay.** `ScheduledTaskWebhookOrigin` in
  [server.ts](../../../../apps/server/src/server.ts) has a `relayHookBaseUrl` from T3 Connect's
  tunnel or none. No setting names a public origin.
- **The runner route always mounts.** `server.ts` provides `RunnerRoute.layer` on the member
  listener whatever drivers are configured. Docker machines dial the runner's Unix socket.
- **Four effect slots, partly bounded.** `DEFAULT_EFFECT_WORKER_CONCURRENCY` is 4 and
  `EFFECT_TIMEOUTS` bounds only sandbox effects and `delegated-tasks.stop`
  ([EffectWorker.ts](../../../../apps/server/src/orchestration-v2/EffectWorker.ts)).
  `checkpoint.capture` and `provider-turn.start` have no bound. The outbox's claim query already
  keeps `thread-title.generate` in its own lane per thread
  ([EffectOutbox.ts](../../../../apps/server/src/orchestration-v2/EffectOutbox.ts)).
- **Retries are fast.** The effect worker's backoff starts at 100 ms and doubles, so five attempts
  end within about 2 s. A driver's `429` or capacity error fails a sandbox almost at once until 2.4
  lands, so 2.4 ships before M5's EC2 driver, where those errors are routine.
- **A delayed retry blocks its thread's queue.** A pending effect with an earlier rowid blocks newer
  ones whatever its `available_at`. A `sandbox.start` waiting 120 s on `retryAfterMs` holds the owner
  thread's next effects, such as a checkpoint capture. That is acceptable for a sandbox that can't
  run anyway, but 2.4's tests must show other threads' effects keep moving.
- **Idle sleep is a guarded worker command.** The Scheduler has no wake-time API; it ticks every 5 s,
  and workers keep their next deadline in a `DueHint`
  ([UsageLimitRecoveryWorker.ts](../../../../apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts)).
  A rejection keeps its receipt for good, so each `sandbox.auto-sleep` takes a fresh id, as
  `thread.auto-settle` does.
- **Presence can't be the viewer signal.** Clients report presence only while another member is
  connected ([presenceReporting.ts](../../../../packages/client-runtime/src/presenceReporting.ts)), so
  the viewer lease is its own small RPC.
- **The reconciler destroys strays.** `ORPHAN_GRACE_MS` (5 minutes) in
  [SandboxReconciler.ts](../../../../apps/server/src/sandbox/lifecycle/SandboxReconciler.ts) is all
  that stands between a restored database and destroying machines created after its snapshot.
- **A release host already exists as a setting.** `pinnedRuntime.ts` and `t3 update` read
  `T3CODE_RELEASE_BASE_URL` ([cliRelease.ts](../../../../packages/shared/src/cliRelease.ts)), so a
  Pair release on the fork's GitHub releases installs through the existing trial and rollback.

### 2.1 `feat(server): sleep idle sandboxes from the scheduler`

- **Scope:** `SandboxLifecycleWorker` in full: `idleDecision(inputs, now)` as a pure table-tested
  function, the viewer lease (an in-memory map renewed by a new `sandbox.viewing` RPC every 5 minutes
  while a cloud session is visible and focused, expiring after 6), the approval hold (2 hours, then
  interrupt with a message), cap pressure (a `ready` sandbox idle 5 minutes sleeps early when a
  waiter queues), and the 7-day archived and 30-day asleep destroys. Settled threads still stop at
  once, as in M1, but the settle-sleep check becomes a driver capability instead of
  `driver.kind === "docker"` in
  [SandboxLifecycleWorker.ts](../../../../apps/server/src/sandbox/lifecycle/SandboxLifecycleWorker.ts),
  so EC2 can opt in. Sleep without 2.7 falls back to 1.33's reads from the latest checkpoint.
- **Takes:** 04 §10 #11; 08 §9 2.9 (the viewer lease).
- **Needs:** M1 (1.18's admission lock, 1.19's worker).
- **Code:** `UsageLimitRecoveryWorker`'s `DueHint` pattern; `thread.auto-settle`'s guard rules for
  rejecting when an input became live; the `sandbox_threads` membership table from 1.3 for inputs
  across attached threads.
- **Decide first:** #2.

### 2.2 `feat(server): wake sandboxes from threads, terminals, MCP, the CLI and restores`

- **Scope:** one explicit `sandbox.wake` per trigger in 04 §2: opening the thread (visible and
  focused), typing in an asleep terminal or pressing **Wake**, MCP and CLI tools that send, run or
  read files, scheduled tasks, checkpoint restore. Never from subscriptions, search, push or mirror
  diffs. Restore, revert and rewind park the rollback effect until `ready` (07 §2), with the test
  draining the effect worker through `waking`. A wake on a settled thread keeps the machine up:
  today the settle rule stops it a second after it starts (progress), so the rule fires only on the
  settle transition.
- **Takes:** 04 §10 #12; 07 §10 #15.
- **Needs:** 2.1.
- **Code:** wakes of a `waking` or `ready` sandbox are no-ops on dispatch's no-event allow list, so
  they don't record rejections; ids name the owner (`sandbox-wake:<id>:<owner>:<generation>`).
